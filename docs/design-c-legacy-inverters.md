## 1. データ構造の約束

### 1-1. 旧機種30件が `ratedCurrentA` / `ratedCapacityKVA` をキーごと持たない理由

30件の `specs` は全件が次の3キーだけです（`data/inverter.json` 実測）。

```json
"specs": { "ratedPowerKW": 3.7, "voltage": "3相200V", "voltClass": 200 }
```

**理由は「出典に書かれていないから」です。** 30件の出典は置換え資料
BCN-C21002-214C ただ1つで、これは定格表ではなく置換え対応表です。
各レコードの `evidence.model.srcNote` にそのまま書かれています。

> 「…p.2「１．寸法」の置換え対応表。適用モータ容量・電源電圧は data/legacy/\*.tsv
> （同資料から起こした対応表）の motorKW / phaseIn / voltageIn 列。
> **定格出力電流・定格容量・外形寸法は同資料に記載が無いため未登録。**」

`0` で埋めない理由は README.md の「データの約束」に書かれています
——「`0` を番兵に使うと、ガードを1つ忘れた瞬間に『0同士だから完全一致』という
誤判定になる」。

`ratedPowerKW`（適用モータ容量）だけは資料にあり、かつ**必須**です。
理由はコミット 5fd859f に書かれています。

> 適用モータ容量は検索の正規化衝突（FR-E720-1.5K / FR-E720-15K、
> FR-E740-1.5K / FR-E740-15K）で見分ける材料になるので必須。

`normLoose` は小数点を落とすため、この2組は検索で同じ綴りになります
（`src/core/util.mjs` / README.md「型式の正規化は『集める』と『見分ける』で分ける」）。
容量が無いと、曖昧一致リストに10倍容量の違う2機種が見分けられないまま並びます。

定格を持たないことの帰結として、旧機種は互換判定の窓（`withinWindow`）に
一切かかりません。`gate` を通れるのは先頭の後継品バイパス
`a.id === m.successorId`（`src/categories/drive.mjs:60`）だけです。

#### これを守っている検査

| 検査 | 名前 |
|---|---|
| `test-compat` 2 | 旧機種30件は定格出力電流・定格容量をキーごと持たず、適用モータ容量だけを持つ |
| `test-compat` 1 | 現行品40件すべてが定格出力電流と定格容量を持つ |
| `test-compat` 14 | 旧機種30件の候補は登録した後継品ちょうど1件 |
| `test-compat` 16 | 現行品を基準にしたとき候補に旧機種が1件も混ざらない |
| `verify-data` 13 | 検索で同じ綴りになる型式に見分ける材料がある（衝突 8 組） |
| `verify-legacy` 7 | 未取得を表す埋め草（0 / - / -- / 不明 / N/A / なし）がどの列にも入っていない |
| `verify-legacy` 10 | motorKW と specs.ratedPowerKW が一致する |

`test-compat` 検査1と検査2が対になっている意図は、`tools/test-compat.mjs:63-70` の
コメントに書かれています——「『全件が定格を持つ』を丸ごと外すと、現行品の定格が
欠けても気づけなくなるので、現行品に対する要求はそのまま残し、旧機種には
『持たないこと』を要求する」。

`verify-data` 検査13 が現在検出している衝突8組のうち2組
（`FR-E720-1.5K / FR-E720-15K`、`FR-E740-1.5K / FR-E740-15K`）が旧機種です。
`ratedPowerKW` を落とすとこの検査が落ちます。

### 1-2. `replacementNote` が `note` と別フィールドである理由

`replacementNote` は `{ partType, partModel }` の構造体で、現在5件だけが持っています
（`verify-data` 検査14 の「現在 5 件」）。すべて `data/inverter.json` の旧機種です。

```json
"replacementNote": { "partType": "取付互換アタッチメント", "partModel": "FR-E8AT03" }
```

**理由は「発注に必須の条件が、仕様説明と同じ枠に埋もれるから」です。**
コミット d2b6f0e に数字つきで書かれています。

> 生産終了品の note 25件のうち置換えの条件は5件（インバータのみ）で、残り20件は
> 仕様説明・来歴・データ品質の注記だった。同じ note に同居しているため、発注に
> 必須の「置換えに FR-E8AT03 が必要」が仕様説明と同じ灰色の枠に並び、読み飛ばされる。

同じことが `tools/schema-map.mjs:225-231` の JSDoc にも書かれています
——「分けておけば、表示側は条件だけを後継型式の隣に出せる」。

分けたことで得られる具体的な性質は3つで、いずれもコードから読み取れます。

1. **表示位置を変えられる。** `note` は中立の `.note` 枠（`noteBox`）、
   `replacementNote` は後継品枠の中（`replacementLine`）。→ 2-2 節
2. **表示側に型式を直書きしなくてよい。** `src/core/ui.mjs:109-114` の
   `replacementLine` は `partType` / `partModel` を読むだけで、
   `FR-E8AT03` という文字列はコードのどこにも無い。
3. **機械照合ができる。** `partModel` が構造化されているので、
   TSV の `note` 列（「置換えに FR-E8AT03 が必要」という1文）から
   正規表現で型式を取り出して突き合わせられる（`verify-legacy` 検査13）。

`note` に同じ情報を残さない理由は、二重管理の禁止です（コミット d2b6f0e:
「note には残さない（二重管理の禁止）」）。これは検査で機械的に止めています。

#### これを守っている検査

| 検査 | 名前 |
|---|---|
| `verify-data` 14 | replacementNote を持つのは生産終了品だけ（現在 5 件） |
| `verify-data` 15 | replacementNote の partType / partModel が両方とも非空文字列 |
| `verify-data` 16 | replacementNote を持つレコードは note を持たない（二重管理の禁止） |
| `verify-legacy` 13 | TSV の note 列と replacementNote が一致する |
| `smoke` 49 | 後継品枠の中に品名と型式（取付互換アタッチメント / FR-E8AT03）が出る |
| `smoke` 52 | 置換えの条件を持たない生産終了品の後継品枠には、その行が出ない |

`verify-data` 検査15 は宣言（`REPLACEMENT_NOTE_KEYS = ['partType', 'partModel']`）に
無いキーも弾きます。`partType` が非空必須なのは、`tools/smoke.mjs:311-317` の
コメントによれば「型式だけでは何を買えばよいのか電話で伝えられないため」です。

### 1-3. `data/legacy/*.tsv` と `data/inverter.json` の役割分担

**TSV が原文台帳（単一の情報源）、JSON が表示用データです。**
`tools/verify-legacy.mjs:1-16` の JSDoc がそのまま定義になっています。

> legacy の TSV は「カタログから読み取った生の対応表」を人手で置く場所で、
> data/\*.json のようにスキーマで守られていない。（…）
> さらに、同じ情報が TSV と data/inverter.json の旧機種30件の2箇所にある。
> 片方だけ更新されても画面は動いてしまうので、**TSV を単一の情報源として
> JSON 側を機械照合する**（検査8〜13）。TSV の綴りが資料どおりであることは
> 人が資料と見比べて担保し、そこから先の写し崩れはこの検査が止める。

つまり信頼の境界は次のようになっています。

```
資料 BCN-C21002-214C  ──人が目で写す──▶  data/legacy/*.tsv  ──検査8〜13──▶  data/inverter.json
                       （ここは機械化されていない）              （ここは機械化されている）
```

TSV は13列固定で、列順まで検査で固定されています
（`model, series, phaseIn, voltageIn, phaseOut, voltageOut, motorKW,
ratedCurrentA, capacityKVA, successors, srcModel, srcSpec, note`）。
`ratedCurrentA` / `capacityKVA` / `srcSpec` の列は**存在するが全行が空**です。
資料に記載が無いためで、`0` や `-` で埋めていません（コミット f660a89・b00d057）。

JSON 側だけが持つもの／TSV 側だけが持つものは次のとおりです。

| 項目 | TSV | JSON | 備考 |
|---|---|---|---|
| 型式・シリーズ・容量・電源 | ○ | ○ | 検査9・10・11 で照合 |
| 後継 | `successors`（型式名） | `successorId`（レコードID） | 検査12 で ID を解決して照合 |
| 置換えの条件 | `note`（1文） | `replacementNote`（構造体） | 検査13 で `partModel` を照合 |
| `partType` | × | ○ | 資料 p.26「４．オプション」由来。検査13 は突合対象にしない |
| 出典URL・`checkedAt`・`evidence` | × | ○ | JSON 側だけ |
| `phaseOut` / `voltageOut` | ○ | × | JSON に対応キーが無い |

TSV を段1の昇格後も残す方針は `docs/handover-magnet-compat-v2.md:384-388`（7-4節）に
記録されています。TSV を消さない代わりに、2箇所の食い違いを検査で塞いだ、
という順序です（コミット c7aceb6: 「一度その場限りのスクリプトで突合したが、
リポジトリに残らず継続的には守られていない」）。

#### これを守っている検査

TSV 自体の規約（検査1〜7）と、TSV ⇔ JSON の照合（検査8〜13）の全13項目が
この役割分担を守っています。とくに役割分担そのものを表しているのは次の6件です。

| 検査 | 名前 |
|---|---|
| `verify-legacy` 8 | TSV の行数と data/inverter.json の旧機種件数が一致する（TSV 30 行） |
| `verify-legacy` 9 | TSV の型式と JSON の旧機種が過不足なく1対1で対応する |
| `verify-legacy` 10 | motorKW と specs.ratedPowerKW が一致する |
| `verify-legacy` 11 | phaseIn / voltageIn と specs.voltage / specs.voltClass が一致する |
| `verify-legacy` 12 | successors と successorId が指すレコードの model が一致する |
| `verify-legacy` 13 | TSV の note 列と replacementNote が一致する |

検査13 は書式に合わない行を黙って読み飛ばしません
（`tools/verify-legacy.mjs:326`: 「読み飛ばすと『解析できないから一致とみなす』になる」）。
また、対応する行が無いケースを拾うため、`note` 列が非空の行数と
`replacementNote` を持つレコード数の一致も見ています。

### 1-4. `primaryStanding` の設計（段4 / PR #19）

> **この節をここに置いた理由。** 大小判定そのものは表示機能なので 2章 に置くことも
> できますが、`primaryStanding` の設計上の核は**「値が無い」という状態をどう運ぶか**で、
> それは 1-1 節が書いた「旧機種30件が `ratedCurrentA` をキーごと持たない」という
> データの性質の直接の帰結です（`'unknown'` の経路がまさにそれ）。1章の続きとして
> 読めるほうが筋が通るので、1章の末尾に置きました。新章を起こさなかったのは、
> 章番号を挿し込むと 4章以降が繰り上がり、**変更してはならない 6章の番号まで動く**ためです。
> 画面にどう出るかは 2-4 節に分けて書いてあります。

#### 1-4-1. 返り値が4つある理由

`numericStanding`（`src/core/registry.mjs:79-100`）は4値を返します。
JSDoc に列挙がそのまま書かれています。

| 値 | 意味 |
|---|---|
| `'below'` | 基準より小さい |
| `'atOrAbove'` | 基準以上 |
| `'unknown'` | 大小に意味はあるが、この組は値が無くて比較できない |
| `null` | そのカテゴリでは大小を判定しない（`registerCategory` の既定） |

**4つある理由は、`'unknown'` と `null` をどちらも `'atOrAbove'` に倒せないからです。**
JSDoc は 2つを別々の理由で分けています。

- `'unknown'` を `'atOrAbove'` に倒さない理由（`src/core/registry.mjs:89-93`）：

  > 片方でも値が無いときに 'atOrAbove'（＝安全側に見える方）を返してはいけない。
  > 値の不在は README の「データの約束」どおりキーの不在で表されるため、`??` で
  > 0 を補って比較すると「0 は基準より小さくない」といった、根拠のない判定が
  > 静かに混ざる。旧機種インバータ30件は定格出力電流をキーごと持たないので、
  > この経路が実際に走る（`tools/test-compat.mjs` 検査2）。

  これは 1-1 節の「`0` を番兵に使わない」（README.md「データの約束」）と同じ話が、
  判定側に現れたものです。実装は `typeof` で数値かどうかを見るだけで、
  `??` による既定値の補完を一切していません（`src/core/registry.mjs:96-99`）。

- `null` が別値である理由（`src/core/registry.mjs:28-29`）：

  > 既定は「判定しない」。大小に意味があるかはカテゴリ固有の知識なので、
  > 宣言していないカテゴリでコアが勝手に大小を語らない（新カテゴリの既定も同じ）。

  `'unknown'` は「このカテゴリでは大小に意味があるが、この1組は比べられない」、
  `null` は「このカテゴリでは大小に意味が無い」で、指している対象が違います。

表示上は `'atOrAbove'` / `'unknown'` / `null` の3つとも無印になりますが、
`belowCount`（`src/core/ui.mjs:159-168`）が数えるのは `'below'` だけで、
`'unknown'` を小さい側にも大きい側にも寄せません。

#### 1-4-2. `'atOrAbove'` に表示を出さない理由

`standingMark`（`src/core/ui.mjs:203-219`）は `'below'` 以外で空文字を返します。
理由は JSDoc にあります。

> 出すのは 'below' のときだけ。'atOrAbove' に「基準以上」と出すと、それ自体が
> 使えるという保証に読める（実負荷を確認しないと決まらないのは大きい側も同じ）。
> 'unknown' と null に何も出さないのは、判定していないものを判定したように
> 見せないため。どちらも無印になるが、その断りは loadCheckNote が引き受ける。

「無印」が `'atOrAbove'` と `'unknown'` の2つを兼ねてしまう点は、
表示を消すことではなく**注意書きで断る**ことで処理しています
（`src/core/ui.mjs:192-194`：「無印が『基準以上』と『比較できる値が登録されていない』の
2つを兼ねるため。無印を黙って『基準以上』と読ませない」）。
その1文は `loadCheckNote` の3文目「表示が無い候補は、基準以上か、比較できる値が
登録されていないかのどちらかです。」で、`smoke` 78 が全6カテゴリで固定しています。

#### 1-4-3. 判定をカテゴリ側に置いた理由

コアが持つのは `numericStanding`（キーを引数で受け取る共通部品）だけで、
**どのキーを渡すか・そもそも判定するかはカテゴリが決めます。**
`src/core/registry.mjs:28-29` の「大小に意味があるかはカテゴリ固有の知識」が理由です。

実際、同じ「主スペックの数値」でも意味が揃いません。読み取れる範囲を並べると：

- 定格使用電流・定格出力電流は「小さい＝要注意」の一方向
  （`src/categories/contactor.mjs:46-54`、`src/categories/drive.mjs:71-78`）
- 検出距離も「小さい＝そこまで届かない」で向きが一致する
  （`src/categories/sensor-common.mjs:75-82`、`src/categories/sensors.mjs:18-24`）
- 整定電流調整範囲は `{min, max}` の区間で、そもそも大小が定義できない
  （`src/categories/thermal.mjs:44-52`）
- 導光路長は「短い＝届かない」と言い切れない（`src/categories/sensors.mjs:44-51`）

コアからはこの4つを区別できません。区別できるのは、そのカテゴリの物理量を
知っている側だけです。

#### 1-4-4. `standingNote` をカテゴリが持ち、前後2文をコアが持つ理由

注意書き `loadCheckNote`（`src/core/ui.mjs:180-201`）は3文でできています。

| 文 | 持ち主 | 実際の文面 |
|---|---|---|
| 1文目 | コア | 「基準より小さい」は、交換前の機器の登録値との比較です。 |
| 2文目 | **カテゴリ**（`standingNote`） | 電流系：実際の負荷電流は定格とはかぎらないので、現場で確認してください。／距離系：実際に必要な検出距離は設置条件で決まるので、現場で確認してください。 |
| 3文目 | コア | 表示が無い候補は、基準以上か、比較できる値が登録されていないかのどちらかです。 |

分割の理由は `src/core/ui.mjs:188-190` とコミット `ff9c601` に同じ趣旨で書かれています。

> 前後の2文（何と比べたのか／表示が無い候補は何なのか）は**このアプリの挙動の説明**
> なのでコアが持つ。真ん中の1文だけが物理量ごとに変わるので、カテゴリから受け取る。
> 全文をカテゴリに持たせると、挙動を変えたときに全カテゴリの文面を直して回ることになる。

この分割は**実際に起きた不具合の後始末**です。`ff9c601` によれば、
「実際の負荷電流は定格とはかぎらない」がコアに直書きされていたため、
検出距離を主スペックに持つセンサ3カテゴリの画面にも同じ文が出ていました。
2文目だけをカテゴリに移し、前後2文はコアに残す形にしています。

インバータの `standingNote` は接触器と同じ文面ですが、文字列は
`src/categories/drive.mjs:85` に別に持っています。理由は同ファイル 80-84 の JSDoc です
——「カテゴリどうしは互いに import しないので、文はここに持つ（インバータが接触器の
文言に追随する関係ではない。多重定格の話を足すなら、直すのはこの1行）」。
一方、電磁接触器と電磁開閉器は同じ `CURRENT_STANDING_NOTE` 定数を共有しています
（`src/categories/contactor.mjs:63`）。同じファイル内で同じ量を判定しているためで、
`contactor.mjs:57-62` に「電磁開閉器も同じ量で判定しているので同じ文を使う」とあります。

#### 1-4-5. `registerCategory` の既定を空文字にし、中立文を当てた理由

`registerCategory` は `standingNote` の既定を **空文字**にしています
（`src/core/registry.mjs:35`）。空のときに実際に画面へ出る文は
`src/core/ui.mjs:178` の `NEUTRAL_STANDING_NOTE`
「実際に必要な値は現場の条件で決まるので、現場で確認してください。」です。

既定を電流の文にしなかった理由は `src/core/registry.mjs:31-34` にあります。

> 大小が何の話なのかもカテゴリ固有の知識。既定は空にしておき、
> 用意し忘れたカテゴリには loadCheckNote が量に依らない中立文を当てる。
> ここに電流の文を既定として置くと、宣言を忘れた瞬間に検出距離の画面へ
> 「実際の負荷電流は…」が出る（実際に起きた）。

`src/core/ui.mjs:170-176` も同じことを、中立文の側から書いています
——「中立文はぼやけるが、掛からない量の話をするよりはよい」。

**つまり既定は「無難な文」ではなく「間違えようがない文」に倒してあります。**
`standingNote` を宣言し忘れたカテゴリの画面はぼやけた文になりますが、
掛からない物理量の話は出ません。

#### 2-4-2. 候補カードに渡す添字を分割前の通し番号のままにした理由

`zone()` は分割後の配列を回しながら、添字だけは元の `list` から引き直します。

```js
const zone = (cs) => cs.map((c) => candidateCard(cat, m, c, list.indexOf(c))).join('');  // app.mjs:327
```

理由は直上の JSDoc（`src/core/app.mjs:320-326`）にあります。

> `candidateCard` は添字0に「候補No.1」バッジを付ける。ゾーンごとに数え直すと、
> 公式後継の隣で判定候補の先頭が「候補No.1」を名乗ることになり、
> 分けた意味（根拠が違う）が見た目で消える。

`candidateCard`（`src/core/ui.mjs:222-227`）は `isSuccessor` なら
「メーカー後継品」バッジ、そうでなくて添字が0なら「候補No.1」バッジを出します。
どのカテゴリの `rank` も後継品を先頭に置く（`src/core/app.mjs:290-292`）ので、
**後継品が居る画面では通し番号0番が後継品になり、「候補No.1」バッジは
どこにも出ません。** ゾーンごとに数え直すと、判定側の先頭がこのバッジを取ります。

> **読み取れないこと：** この添字の扱いを固定する検査は、`npm run check` の出力の中に
> 見当たりません。「候補No.1」という文字列を見る検査は `tools/smoke.mjs` に1つもなく、
> `zone()` をゾーンごとの `index` に書き換えても `npm run check` は通ります。
> 意図的な省略かどうかは、コメント・コミットメッセージのいずれからも読み取れません。

### 3-2. `.cmp b` の CSS 詳細度を下げず、`span` で回避している

**事実：** `src/index.html` に次の2つのルールがあります。

`.cmp b` は詳細度がクラス1＋要素1、`.amber` はクラス1なので、**後継品枠の中で

`src/core/ui.mjs:107-108` はこの回避策を明記しています。

> クラスの有無だけを見ていた検査は、その書き換えを通してしまい画面だけ色が落ちる。

足す、`!important` を使う、など）ではなく `span` を選んだのか、その判断理由は
コメント・コミットメッセージ・検査のいずれからも読み取れません。**
6c81c12 は「実装は変更していない」と結果だけを述べており、そのPRの目的が

単にそのPRの範囲外だったのかは区別できません。上の「影響範囲」も
事実として読み取れるだけで、それが選択の理由だったとは書かれていません。

同じ扱いをしていません。** どちらも既定値を与えるだけで、宣言が無くても登録は通ります
（`src/core/registry.mjs:30・35`）。

読み取れる理由は2つあります。

1. `src/core/registry.mjs:28-29` が「宣言していないカテゴリでコアが勝手に
   大小を語らない（新カテゴリの既定も同じ）」と書いており、**未宣言は誤りではなく
   「判定しない」という有効な状態**として扱われています。判定しない3カテゴリ
   （`thermal` / `special` / `servo`）は実際に `() => null` を明示していますが、
   既定と同じ値なので、省いても挙動は変わりません（1-4-6 節）。
2. 落とす設計にすると `test-extensibility` が通りません。同テストが書き込む
   ダミーカテゴリ（`tools/test-extensibility.mjs:44-52`）は `primaryStanding` も
   `standingNote` も宣言しておらず、それでも検査4「互換判定が動く」まで到達します。
   `npm run check` の最後に出る「カテゴリ追加は2ファイルで完結」は、
   **必須の宣言を増やさなかったこと**を含めての結果です。

**同じ場面で検査側は逆に倒しています。** スモークの `specNumber`
（`tools/smoke.mjs:544-556`）は解けない書式を `NaN` にして呼び出し側を必ず落とします。
表示側は「判定しない」に倒し、検査側は落とす、という向きの違いです
（2-4-3 節・`tools/verify-legacy.mjs:326`）。

**読み取れないこと：** 例外を投げる案が検討されたうえで見送られたのか、
最初から候補になかったのかは、コミットメッセージ・コメントのいずれからも
読み取れません。

#### 3-4-2. モックの見出し「同じ容量帯の型式」を使わなかった

**事実：** 引き継ぎ書のモック（`docs/handover-magnet-compat-v2.md:259-261`）は
判定側のゾーンをこう書いていました。

```
■ 同じ容量帯の型式（当アプリの判定）
  メーカーが後継として指定したものではありません。
  容量が足りない機種も含みます。
```

実装は見出しを **「当アプリの判定による候補」** にし、添える1文は
「メーカーが後継として指定した型式ではありません。」の1文だけです
（`src/core/app.mjs:332-333`）。「容量が足りない機種も含みます」は入っていません。

読み取れる理由は2つあります。

1. **見出しの役割が「量」ではなく「根拠」だから。** `zoneHead` の JSDoc
   （`src/core/ui.mjs:143-153`）は見出しの目的を「見出しで根拠を分けて、後者が
   メーカーの保証ではないことを列の入口で言う」と書いています。
   `zoneHead` は9カテゴリ共通で、主スペックは定格電流・検出距離・整定範囲・
   導光路長と量がばらばらです（1-4-6 節）。「容量帯」はそのうち電流系3カテゴリ
   にしか掛かりません。
2. **「容量が足りない」は書かないと決めた表現だから。** `loadCheckNote` の JSDoc
   （`src/core/ui.mjs:183-186`）が「『容量不足』『使用不可』と書くと、成立する置換えを
   現場が捨てることになる」と書き、`smoke` 62「③に『容量不足』『使用不可』など
   適合の可否を断定する文言を出さない」が正規表現 `/容量不足|容量が足りな|使用不可/`
   で機械的に止めています。モックの「容量が足りない機種も含みます」は
   **この検査に直接引っかかる文面**です。

**読み取れないこと：** モックの見出しを採らないと明記した記述は、
コミットメッセージ・コメント・検査のいずれにもありません。上の2つは
実装と検査から逆算して読み取れる理由で、当時そう判断した記録ではありません。
→ 5章9

#### 3-4-3. モックの「Pr.570 等のパラメータ再設定」を実装しなかった

**事実：** モック（`docs/handover-magnet-compat-v2.md:257`）は後継品枠に
「⚠ Pr.570 を ND定格に。Pr.800 / Pr.162 も再設定」という行を置いていました。
実装にこの行はありません。後継品枠に出るのは `replacementLine`
（`partType` / `partModel`）だけです（2-2 節）。

読み取れる理由は、**そのデータがリポジトリに無いこと**です。

- `replacementNote` の許容キーは `partType` と `partModel` の2つだけで、
  `verify-data` 15 が宣言（`REPLACEMENT_NOTE_KEYS`）に無いキーを弾きます（1-2 節）。
  パラメータを入れる場所が定義されていません。
- 原文台帳 `data/legacy/*.tsv` は13列固定で、パラメータの列がありません（1-3 節）。
- パラメータ対応表そのものが一次資料からリポジトリへ写されていません。
  `docs/fr-e700-to-e800-replacement.md:242-244` にそう書かれています。

  > 資料A p.19〜25 に、E700 → E800 のパラメータ対応表（約200項目）がある。
  > 本ファイルには転記していない。必要になった時点で別ファイルとして起こすこと。

  同ファイル 247-253 に載っている5項目は「特に注意を要する項目のみ」の抜粋で、
  `data/` のどのレコードにも入っていません。`data/inverter.json` で `Pr.570` に
  触れているのは現行品40件の `note`（ND定格の説明）だけです。

つまり 1-1 節と同じ形の話で、**出典に無いものは登録しない**という
このリポジトリの既定の帰結です。

**読み取れないこと：** 「段4では実装しない」と決めた記述は見当たりません。
`docs/fr-e700-to-e800-replacement.md:244` の「必要になった時点で別ファイルとして
起こすこと」が唯一の関連記述で、これは段4より前に書かれたものです。

#### 3-4-4. 近接スイッチに `'below'` の名指し検査を作らなかった

**事実：** `primaryStanding` を宣言する6カテゴリのうち、
「基準より小さい候補に表示が出る」を名指しで見る検査があるのは5つです。

| カテゴリ | 名指しの検査 |
|---|---|
| 電磁接触器 | `smoke` 59・60・61（S-N35） |
| インバータ | `smoke` 66・67（FR-E820-5.5K-1） |
| フォトスイッチ | `smoke` 68・69（E3Z-D61） |
| 電磁開閉器 | `smoke` 70・71（MSO-N20） |
| 超音波センサ | `smoke` 72（US-T50） |
| **近接スイッチ** | **無し** |

コミット `18b2bad` は足した4カテゴリを列挙していますが、近接スイッチは
その4つに入っていません（「インバータ・フォトスイッチ・電磁開閉器・超音波センサも
1画面ずつ通す」）。

**ただし `'below'` の経路が通っていないわけではありません。** 近接スイッチは
`NOTE_SCREENS` に `E2E-X12C318` として入っており（`tools/smoke.mjs:680`）、
検査73「注意書きを出す6カテゴリすべてで、文面が空でない」・検査76・検査78 が
その画面の `.load-note` の全文を要求します。`loadCheckNote` は
`belowCount` が0なら空文字を返す（`src/core/ui.mjs:196-197`）ので、
**この3件が通ることは、その画面に `'below'` の候補が1件以上あることを意味します。**
名指しの検査が無いのは「基準より小さい候補にその表示が出ること」のほうです。

**読み取れないこと：** 近接スイッチだけ名指しの検査を作らなかった理由は、
コミットメッセージ・コメント・検査のいずれからも読み取れません。→ 5章10

### 6-1. `scopeNote` を `discontinuedNote` より先に出す理由（5章1）

**理由：この2つは伝えている層が違い、`scopeNote` のほうが下の層にあるからです。**

`scopeNote` が言っているのは「この行はシリーズ単位のマスクであって、
個別の発注可能型式ではない。実機の銘板を見て型式を確定させよ」です。
これは **どの型式の話をしているのかを確定させる指示** で、
その型式が現行品か生産終了品かという問いより手前にあります。

型式が確定していない状態で「この型式は生産終了です」と先に読ませると、
`SGDM / SGDH / SGDP / SGDJ / SGDD` というマスク全体が生産終了だと受け取られます。
実際にはこのマスクに含まれる個別型式のうち何が該当するかは、
銘板を見るまで決まりません。

したがって現在の順序は正しく、**変更しません。**

現在この情報は画面のどこにも出ていない」と書きました。**事実と違いました。**
`ui.mjs` の `noteBox` が `app.mjs` から呼ばれており、②画面の `.note` 枠に
既に描画されていました。

原因は、実機の**③画面のスクリーンショットだけを見て、②も同様だと推定した**ことです。
実装セッションが実測（`note el: 置換えに FR-E8AT03 が必要`）を示して訂正してきました。

#### 誤り3が生んだ不具合：全20件の仕様説明に ⚠ が付いた

段3の指示に「`note` の内容も併記する」と書いたことで、
`discontinuedNote` が生産終了品の `note` を無条件に警告枠へ取り込む実装になりました。
その結果、光電・近接・サーマルの20件（仕様説明・来歴）にも ⚠ が付き、
`GX-8M` では `note` 本文が既に含む ⚠ と二重になりました。

**指示を書いた時点で見ていたのはFR-E700の5件だけで、
他カテゴリの生産終了品が持つ `note` の性質を確認していませんでした。**
これが `replacementNote` 分離（PR #15）に至った直接の原因です。

#### 共通する原因と、実際に効いた対策

3件とも原因は同じで、**実測せずに推測を指示に混ぜたこと**です。

対策として実際に機能したのは次の3つでした。

| 対策 | 効果があった場面 |
|---|---|
| **検査を意図的に壊して `exit=1` を確認させる** | 段3で `noteBox` を消したら新設46番だけでなく既存40番・63番も落ち、note経路が三重に守られていることが判明した |
| **「指示に辻褄を合わせず、実測と食い違えば報告せよ」を毎回明記する** | 誤り2 の訂正はこれによる。実装セッションが指示を疑って実測した |
| **監査は新規セッションで行う** | 誤り1 の発覚はこれによる。同じセッションに自分の成果を評価させない |

**この文書自体も同じ枠組みで作られています。** 実装したセッションではなく
新規セッションに、コードと検査とデータだけを根拠として書かせました。
