PR #24 で、コアの既定文だった

> 互換候補が登録されていません。

## 1. 何を数えたか

`sensorGate`（`src/categories/sensor-common.mjs:99`）は次の順で判定する。

```
1. 出力極性が交わらない        → 落とす
2. 配線本数が食い違う          → 落とす
3. メーカー指定の後継品         → 通す
4. compatKey が一致            → 通す
5. compatGroup が一致          → 近接はねじ径一致、他は検出方式の互換で通す／落とす
6. どれにも当たらない          → 落とす（key も group も共有しない）
```

**極性・配線は key/group の判定より前にある。** そのため判定順にだけ数えると、
そもそも互換系列を共有しない相手まで「配線本数で落ちた」に数え上げられる。
これは画面の説明としては効いていない除外なので、集計を2通り出す。

| 集計 | 定義 | 何が分かるか |
|---|---|---|
| **判定順** | `sensorGate` と同じ順で「最初に落ちた条件」を数える | 依頼の【1】が指定した集計そのもの |
| **実効** | 極性・配線の2条件を外したら通っていたか | その2条件が **この画面の結果を決めたか** |

「実効で通る」＝ 極性・配線さえ食い違わなければ候補になっていた相手。
現行文面の後段が指しているのはこの相手のことなので、真偽の判断はこちらで見る。

### 4-2. GX-4M — 現在の文面が偽になる1件

| 項目 | 値 |
|---|---|
| compatKey | `PX-GX4M`（他に持つ型式なし） |
| compatGroup | `PX円柱`（他に19件） |
| ねじ径 | `M4?` |
| 出力方式 | `NPN NO(3線式)` |

`compatGroup` を共有する19件はすべてねじ径が違う。近接は `compatGroup` 経路で
ねじ径の一致を要求する（`sensor-common.mjs:107`）ため、19件は全部そこで落ちる。
判定順では極性2件・配線77件が先に立つが、**その79件は極性・配線を外しても
系列を共有しないかねじ径が違うので、1件も候補にならない**。
`M4?` は `data/proximity.json` で GX-4M だけが持つ値で、他に M4 級のねじ径は無い。

つまりこの画面が0件なのはねじ径が理由で、後段の1文が名指しする2条件は
結果を1件も動かしていない。**現在の文面はこの画面で偽。**

### 4-3. PR-308.A3 / PR-125.A3 — 事前調査に入っていなかった2件

事前調査では 9800-0159 / BS-R80 / LDS-8Aシリーズ の3件が
「極性0件・配線本数0件」で B と見立てられていた。実測すると
**この2件も系列を共有する相手が0件**で、実質は同じ B に属する。

判定順ではこの2件に「配線本数44件」が立つ。しかしその44件は
`compatKey`（`PX-SEJ-8mm` / `PX-SEJ-25mm`、どちらも自身だけが持つ）も
`compatGroup`（両方とも未設定）も共有しないので、配線本数を見る前から候補ではない。
**判定順の件数だけでは B を取りこぼす。** 事前調査が3件だったのはこのためで、
実測の B は5件になる。

### 4-4. 見出しの1文目も同じ問題を持つ

依頼は後段の1文が対象だが、実測の過程で1文目にも同種のずれが出た。

> 互換候補が登録されていません。

**16件中11件は、系列（`compatKey` か `compatGroup`）を共有する型式が
登録済みである。** 判定で外れただけで、未登録ではない。
アプリは検索画面で「実在確認済みのデータが未登録です」（`src/core/app.mjs:235`）を
別の意味で使っており、同じ「登録されていない」という語がデータの欠落を指す。
コア既定文が「互換品候補は見つかりませんでした」と断定を避けている
（`src/core/app.mjs:331`）のに対し、センサー側だけが強く断定している状態。

## 5. 文面の提案と決定

### 5-0. 依頼者の判断（2026-08-24）

**分類は「実効」を正とする。**

> 画面が答えるべきは「なぜこの型式では候補が出ないのか」であって、
> アプリが最初にどの分岐で弾いたかではありません。

この判断により、§4-1 で立場によって割れていた3件の分類が確定する。

| 型式 | 確定した分類 |
|---|---|
| GX-4M | **C**（現在の文面は偽） |
| PR-308.A3 | **B**（後段は何も説明していない） |
| PR-125.A3 | **B**（同上） |

確定後の内訳は **A 10件 / B 5件 / C 1件**。§5 以降はこの分類で書いている。

**判定順の集計（§3）は残す。** 実装の都合で `sensorGate` の分岐順が変われば
判定順の数字は動くが、実効の数字は動かない。両方あることが比較材料になる。
`tools/audit-sensor-empty.mjs` も2通りの集計を出したままにしてある。

### 5-1. 何が問題なのか

現在の後段の1文は **その画面で起きたこと** を語る形をしている。

> 電気的に成立しない組み合わせ（出力極性・配線本数の相違）は候補から除外しています。

しかし `emptyNote(m)` は基準機しか受け取らないので、
**アプリはその画面で何が落ちたかを実行時に知らない。**
知らないことを画面ごとの事実として語っているため、GX-4M で偽になり、
5件で何も説明しない文になる。段4で「容量不足」と書かなかったのと同じ形の問題。

### 5-2. 推奨案 — 「起きたこと」ではなく「候補の必要条件」を語る

（この節は提案時のまま。実装で1点直した。§5-5 を参照）

```
互換品候補は見つかりませんでした。
このカテゴリが候補に出すのは、同じ互換系列にあり、かつ出力極性・配線本数が
食い違わない（電気的に成立する）型式だけです。この型式では、それを満たす
登録型式がありませんでした。どの条件で外れたかはこの画面では判別できません。
```

理由。

1. **16件すべてで真になる。** 「〜だけ」は必要条件の宣言であって、
   その画面で実際にどれが効いたかを主張しない。ねじ径・検出方式を書かなくても
   （それも必要条件なので）偽にならない。GX-4M でも成り立つ。
2. **説明できないことを説明したふりをしない。** 最後の1文で、画面ごとの理由が
   出せないことを明示する。B の5件で「何も説明していない文」が残らない。
3. **センサー固有の情報は残る。** 極性・配線を判定に使うのはセンサー4カテゴリだけで、
   PR #24 がこの文面をここへ移した意図（除外理由を語れるのは条件を持つ側だけ）は保つ。
4. **見出しも直す。** §4-4 のとおり「登録されていません」は11件で誤読を招くので、
   コア既定文と同じ「見つかりませんでした」に寄せる。

`emptyNote(m)` は基準機を受け取るので `m.category` で近接とそれ以外を分け、
近接だけ「ねじ径が同じ」を足すこともできる（`sensorGate` 側も同じ分岐を持つ）。
ただし文面が名指しする条件が増えるほど gate 変更時の追随漏れが増えるため、
**必要条件を全部並べず、電気条件だけに絞る案を推す。**

### 5-3. 採らなかった案

| 案 | 内容 | 採らない理由 |
|---|---|---|
| B | `sensorEmptyNote` を消してコア既定文に戻す | 真にはなるが、極性・配線を判定に使っているのはセンサーだけ、という情報が画面から消える。PR #24 は文面を「条件を持つ側」へ移したのであって、黙らせたわけではない |
| C | `emptyNote` の引数を増やし、画面ごとの理由を出す | `registry.mjs` の署名と全カテゴリに波及する。加えて `gate` は真偽しか返さないので、落ちた理由を集めるには `gate` / `compat.mjs` の変更が要る（今回の禁止事項）。やるなら別PR |
| D | `emptyNote` の中で判定をやり直して理由を出す | 引数は増えないが `sensorGate` の分岐を配布物の中に2つ持つことになる。gate を変えたときに黙ってズレる |

### 5-4. 実装時に足せる検査（提案）

推奨案は「候補に出すのは○○だけ」という **必要条件** を名乗る。これは
`sensorGate` に対して機械的に検算できる。センサー4カテゴリの全ペアで

- `sensorGate` が真を返すなら `polarityOK` が真であること
- `sensorGate` が真を返すなら配線本数が食い違わないこと
- `sensorGate` が真を返すなら後継指定か `compatKey` / `compatGroup` を共有すること

を確かめれば、gate から条件が消えたときに文面だけが残る事故
（インバータで起きたことの一般形）をビルド前に落とせる。
対象0件で全項目PASSになる穴も無い（センサーのペアは常に存在する）。

文面が **その画面で真か** のほうは機械的に決められない。
判定できないものを検査にしないため、そちらは検査にせず
`tools/audit-sensor-empty.mjs` の再実行で見ることにする。

### 5-5. 実装（2026-08-24）

§5-0 の判断を受けて実装した。**§5-2 の文面を1点だけ直している。**

#### 直した点 — 後継品の経路を書き落としていた

§5-2 の「同じ互換系列にあり」は、必要条件として **偽**だった。
`sensorGate` は `compatKey` / `compatGroup` の判定より先に後継品バイパス
（`a.id === m.successorId`）を持つので、互換系列を共有しないまま通るペアがありうる。
実測すると、センサー4カテゴリの後継リンク13ペアのうち1ペアが実際にこれに当たる。

| 基準 | 候補 | compatKey | compatGroup |
|---|---|---|---|
| I-215.95HTF | PR-219.A3HTF | 共有しない | どちらも未設定 |

この1ペアは `sensorGate` を通って候補に出る。「候補に出すのは同じ互換系列にある
型式だけです」と書くと、この画面が反例になる。文面に「メーカー指定の後継品か」を足した。

`node tools/test-sensor-empty.mjs` の検査6 がこの反例を数える。
§5-2 の文面のまま実装していれば、この検査が NG で止まっていた。

#### 入った文面

```
互換品候補は見つかりませんでした。
このカテゴリが候補に出すのは、メーカー指定の後継品か、同じ互換系列として登録された
型式のうち、出力極性・配線本数が食い違わない（電気的に成立する）ものだけです。
この型式では、それを満たす登録型式がありませんでした。
どの条件で外れたかはこの画面では判別できません。
```

#### 検査

| 検査 | 何を見るか |

## 6. 読み取れなかったこと

- **GX-4M のねじ径 `M4?`。** `data/proximity.json` でこの型式だけが持つ値で、
  末尾の `?` が何を表すのかは根拠が無い。M4 相当と読めば同じねじ径の登録型式は
  他に無く、`?` を未確認の印と読んでも同じ結論（0件の理由はねじ径）になるため、
  §4-2 の判断はどちらに読んでも変わらない。データの修正はこの精査の対象外。
- **判定順と実効のどちらを「正」とするか。** 依頼の分類定義は3件（GX-4M /
  PR-308.A3 / PR-125.A3）でどちらの読みにも取れる。本書は両方を併記し、
  文面の真偽を論じる §5 では実効を使った。どちらを採るかの決めは依頼者に委ねる。
  → **解決済み（§5-0）。** 依頼者の判断で「実効」を正とすることが決まり、
  3件の分類は C / B / B に確定した。判定順の集計（§3）は比較材料として残す。
- **9800-0159 の出力方式・電源電圧。** どちらも `⚠要確認` で、
  極性も配線本数も判定できない。この型式については、電気条件が
  「食い違わないから通した」のか「値が無いから判定していない」のかを
  データからは区別できない（`polarityOK` / `wireCount` はどちらも
  値が無ければ判定しない側に倒れる）。ただし系列を共有する相手が0件なので、
  分類 B という結論はこの不明点に依存しない。
