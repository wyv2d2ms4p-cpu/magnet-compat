# 設計文書：予備品が無いときに代わりの機器を示す共通の仕組み

この文書は、`docs/design-insulation-converter.md` 11章の大方針（11-2）を受けて、
**予備品が無いときに同等の機能を持つ機器を探す「共通の仕組み」の形**と、それに対する依頼者の決定を記録するものです。
仕組みはカテゴリをまたぐので、絶縁変換器の設計文書の章ではなく、独立した文書にしました。

- **まだ実装されていません。** この文書は形を決めたもので、コード・検査・データは変えていません。
  いま画面が出しているのは、既存の設計文書に書いたとおりの③です。
- **根拠の書き方。** 各項目に、根拠として次のどれかを添えています。
  - 「設計報告 A-n」… 共通の仕組みの設計報告（プランモードで作成。リポジトリには置いていない）の付録A の節
  - 「依頼者の決定」… 依頼者が決めたこと。日付を添える
  - PR 番号・実測・既存の設計文書の節
- **実測の値は、すべて `fcd064a`（PR #53 のマージ）の時点のもの**です。`data/*.json` をそのまま
  `loadDevices` に読み込み、`computeCompatibles` を全基準機に掛けて数えています（`tools/regress.mjs` と同じ読み込み方）。
  データが増えると変わるので、使うときは数え直してください。
- **絶縁変換器の分類について。** 5章の件数は、実測のためだけに仮に置いた分類で数えたものです。
  仮の分類の各行に出典は付いておらず、分類表の中身の提案ではありません（中身は 3-2 の手順で出典から起こす）。

## 1. 段（候補の区分）

### 1-1. 段は4つ。順番と名前はコアが持つ

| 段の id | 見出し | 何が根拠か | どこから来るか |
|---|---|---|---|
| `successor` | メーカー指定の後継品 | `a.id === m.successorId` | `computeCompatibles` の `isSuccessor`（既存。変えない） |
| `exact` | 判定条件がすべて一致 | カテゴリの `gate` を通った | `computeCompatibles` の戻り値（既存。変えない） |
| `classMatch` | 分類が一致・違いあり | 分類表で同じ分類、登録値に違いあり | 新しい口（カテゴリが任意で宣言） |
| `rework` | 配線変更または台数増が必要 | 名前付きの組み合わせのルール | 新しい口（同上） |

- **根拠** … 見出しの語は 11-2-2（依頼者の決定）。段の持ち方は設計報告 A-1-1。
- **既存の2段は振り分けるだけ。** 今の `viewResult` が `isSuccessor` で2分割しているのと同じ形で、
  `computeCompatibles` の戻り値の中身と順番には触りません（11-2-5）。
- **新しい段は加算の口から足す。** コアに `computeTiers(m, category, ctx)` を置き、
  `{ successor, exact, classMatch, rework }` を返します。前の2つは `computeCompatibles` の戻り値の振り分け、
  後の2つはカテゴリが任意で宣言する `alternates(m, ctx)` の戻り値です。宣言しないカテゴリでは空配列です。

### 1-2. コアが守らせること

カテゴリ側で毎回書かせると、1つ忘れた時点で穴が開きます（`modelScope: 'series'` をコアで落としているのと同じ理由。設計報告 A-1-1）。

1. 1つの型式は1つの段にだけ入る。`successor` / `exact` に入ったものは下の段から除く（上の段が勝つ）
2. 基準機自身と `modelScope: 'series'` のレコードは入れない
3. 候補が指す部品は**登録済みのレコードの id だけ**。`store.byId` で解決できなければ例外で止める。
   **口は型式の文字列を作れない**（引き継ぎ書 §2 ルール2 の歯止め。4-3）

### 1-3. 見出しを出す規則

- **今の規則**（`src/core/app.mjs` の `viewResult`）… 後継品と判定候補の両方に中身があるときだけ見出しを出す。
- **広げた規則** … 「中身のある段が2つ以上」**または**「`classMatch` / `rework` のどちらかに中身がある」とき、
  中身のある段にだけ見出しを出す。
  - 後者を足す理由：下の段の候補が見出し無しで並ぶと、判定条件がすべて一致した候補と区別できない（11-2-1 ①）。
    今の規則だけだと「下の段だけに1件」の画面で見出しが消える（設計報告 A-1-2）。
  - 帰結：口を宣言しないカテゴリでは、今の規則と結果が同じになる。
- **`exact` が0件で下の段だけあるときは、下の段の前に「判定条件がすべて一致する候補はありません。」を1行出す**（D8）。
- カテゴリの0件パネル（`emptyNote`）は**全段が0件のときだけ**出す。見出しの「互換品候補は見つかりませんでした」が
  下の段と矛盾するため（設計報告 A-1-2）。
- `.zone-head` と `.card` は今までどおり `#app` の直下に置く。`smoke` の `resultZones()` は直下の子を文書順に見て
  所属を決めるので、入れ子にすると下の段の候補を拾えない（設計報告 A-1-2）。

### 1-4. 件数の表示

- 見出しを出す画面では、**中身のある段ごとの件数**を出す（今の内訳の文言の形を段の数だけ伸ばす）。
- **全段を足した数を「互換品候補 N件」と呼ばない**（D9）。理由は今のコメントと同じで、
  合算した件数は根拠の違う候補を1つの数字にまとめてしまう（`viewResult` のコメント）。
- 見出しを出さない画面の件数表示は今のまま（`smoke` の `分けていない画面の件数表示は従来どおり内訳を付けない`）。

### 1-5. 「候補No.1」バッジとカードの見た目

- **バッジが付くのは `exact` の先頭だけ**で、条件は今と同じ（戻り値の添字0で、後継品でない）。
  下の段のカードには添字 `-1` を渡し、どんな場合もバッジを付けない。下の段の先頭が「No.1」を名乗ると
  「一番の候補」と読まれる（設計報告 A-1-4）。
- 下の段のカードは今の `candidateCard` を使い、次だけを変える（設計報告 A-1-5）：
  - 別メーカーのバッジの語は **「別メーカー」**（D10）。「互換」を名乗らない（11-2-1 ③）。
    **今の③（`exact` の段）の「他社互換」は変えない**（接触器・サーマルの画面が広く変わるため。D10）
  - `detailPanels` の代わりに確認項目の表（2章）を出す
  - `rework` の段は型式の横に「× 2台」。型式の文字列は登録された綴りのままで、新しい綴りを作らない

### 1-6. 下の段に出さないもの

- **応答が遅い機器、応答時間が型式で決まらない WGP-FV は下の段にも出さない**（D5）。
  遅い側の不具合は動かすまで出ない、という今の判断（9-2・11-3-1）の理由が下の段でも同じため。

## 2. 確認項目

### 2-1. 状態は4つ。印と文言はコアが持つ

| 状態 | 画面の印 | いつ |
|---|---|---|
| `differs` | △ 違う | 両方に値があり、違う |
| `missing` | ？ 未登録・現物で確認 | **片方でも**値が無い（11-2-3） |
| `field` | ◇ 現場で確認 | 値はそろっているが、可否が現場の状態で決まる（スイッチで選ぶ出力・今の整定値など） |
| `same` | ✓ 同じ | 両方に値があり、同じ |

- **根拠** … 設計報告 A-2-1。`missing` を置くことは 11-2-3（依頼者の決定）。
- `missing` は値が無い側を「同じ」にも「違う」にも倒さない。`??` で 0 を補わない（README「データの約束」）。
- 印と文言をコアが持つのは、カテゴリごとに「違う」の言い方を書くと、断定語が1つのカテゴリから混ざるため。
- **「未登録・現物で確認」の印の色は「違う」と同じ橙**（D7）。灰色は今の画面で「寸法未確認」など
  読み流される側の色で、未登録を隠さない決定（11-2-3）の目的が確認漏れを防ぐことだから。

### 2-2. 項目の定義は各カテゴリが持つ

カテゴリが `checkDefs` を任意で宣言します（設計報告 A-2-2）。

```js
checkDefs: [
  { key: 'powerSupply', label: '電源電圧',
    read: (d) => d.specs?.powerSupply,        // 値が無ければ undefined（0 や '' を返さない）
    compare: 'equal',                          // 6章の比べ方の名前
    format: (v) => v,
    whenDiffers: '盤に来ている電源を確認してください。' },
]
```

- 比べ方は 6章の共通の比べ方から選び、結果から状態への対応はコアが決める。
- 文面は「事実（基準の値／候補の値）」と「何を確かめるか」まで。可否は書かない（8-4・9-4-3）。

### 2-3. 既存の `detailPanels` との関係

- **並べて残す。ただし同じカードに両方は出さない**（設計報告 A-2-3）。
  - `exact` の段は今の `detailPanels` のまま。
  - `classMatch` / `rework` の段は確認項目の表だけを出す。絶縁変換器の `checkDefs` は電源電圧・外形寸法・オプションを含め、
    文面は今のパネル（`powerSupplyPanel` など）と同じ言い回しに揃える。
  - 両方を出すと同じ差が枠と表で2回出る。実測では、下の段に入る組の1枚に既存パネルが2〜3枚出る（5-1）。
- **今の③の電源電圧・外形寸法の枠の「片方でも値が無ければ出さない」は、今は変えない**（D6）。
  新しい扱いは下の段だけ。今の枠の扱いは依頼者の決定（9-4-5）で、変えるなら別に決める。
- サーマルの「保護方式」「取付適合」パネルも同じ扱いで、サーマルが使い始めるときに `checkDefs` に同じ中身を持たせる。
  そのとき、パネルの「欠相保護が必要な用途では使用できません。」は、確認項目では
  **「欠相保護が要る回路かを確認してください」の形**にする（D12。断定を避ける）。

### 2-4. 見せ方

設計報告 A-2-4 のとおりにします。

- 1枚のカードの確認項目は、枠を重ねず**1つの表**にする（1行＝項目名・基準の値・候補の値・印）。
- 並び順は状態で決める：**違う → 未登録 → 現場で確認 → 同じ**。
- **「同じ」は1行にまとめる**（例「同じ：入力の相数・第2出力」）。隠さず、数えられる形で残す。
- **違う・未登録・現場で確認は1つも省かない**（件数で打ち切らない）。省くと 11-2-3 の目的に反する。
- 全カードに同じ内容が出る問い（「今の整定値」など）はカードごとに書かず、2-5 の「現場への問い」に1回だけ出し、
  表の行は「◇ 問い1」のように参照する。

実測（`fcd064a`）：`MS3749-A-D44/H` → `WGP-FZ-14FK-1` のカードでは、`specs` のキーで違う・片方に無いものが7つ
（入力信号・第1出力・電源電圧・オプション・第1出力最大周波数・第2出力最大周波数・入力抵抗）あり、この7行が上の規則で並ぶ。

### 2-5. 現場への問い

- カテゴリが `fieldQuestions(m)` を任意で宣言する。**基準機だけを受け取る**（`emptyNote(m)` と同じ制約）。
- 置き場は**③の結果ヘッダの直下、候補より前に1回だけ**（見出し「交換前に現場で確かめること」）。
  問いは基準機の性質から出るので、候補の数だけ繰り返すと同じ文が何十回も並ぶ（設計報告 A-2-5）。
- **問いに答えを入力させて候補を絞る仕組みは、当面作らない**（答えを保存する場所が無く、画面の状態が増える。設計報告 A-2-5）。

| カテゴリ | 基準機の条件 | 問い | 根拠 |
|---|---|---|---|
| 絶縁変換器 | `inputPhases === 2` | B相の配線を使っているか（入力が2回路） | 設計報告 A-2-5。4-2 の組み合わせと合わせて使う（D2） |
| 絶縁変換器 | `output2Signal` がある | 第2出力（OUT2）の配線を使っているか | 設計報告 A-2-5 |
| 絶縁変換器 | 第1出力がスイッチで選ぶ値 | 第1出力のディップスイッチを何に設定しているか | 設計報告 A-2-5・D4 |
| 絶縁変換器 | `outputLogic` がある | 受け側が出力の論理（反転）に合わせて組まれているか | 設計報告 A-2-5 |
| サーマル | 常に | 今の整定値（目盛り）はいくつか | 設計報告 A-2-5・D11 |
| サーマル | `protect === '2E'` | 欠相保護が要る回路か | 設計報告 A-2-5・D12 |
| 接触器 | 常に | 使っている補助接点の数（a接点・b接点） | 設計報告 A-2-5 |
| 接触器 | 常に | 操作コイルの電圧（銘板の表示） | D15 |

### 2-6. チェック欄は置かない

- **確認項目にチェック欄を当面置かない**（D14）。チェックしても保存する場所が無く、画面を戻すと消える。
  付いたチェックが「確認済み」と読まれるため。

## 3. 分類（別メーカー品の比較用）

### 3-1. 信号名とは別に、分類への対応表を持つ

- `specs` の信号名は**資料の表記のまま**（10-1-5）。綴りを寄せると `exact` の段に別メーカー品が入る
  （案A'' の実測：候補の辺 81本 → 83本。11-2-1）。
- 対応表は **`src/categories/insulation-signal-classes.mjs`**（カテゴリのモジュール）に置く。
  - `data/reference/` に置かない理由：`build.mjs` は `reference/makers.json` だけを名指しで読むので、置くと `build.mjs` の変更が要る
    （README「コアにも build.mjs にも手を入れる必要がない」に反する）。`src/categories/` のモジュールは `build.mjs` が自動で拾う。
    （根拠：設計報告 A-3-1。`build.mjs` の該当箇所を `fcd064a` で読んで確認）
- 1行の形（設計報告 A-3-1）：

```js
{ field: 'input',  spelling: '無電圧スイッチ', classes: ['接点・オープンコレクタ入力'], mode: 'single',
  src: '<設計文書の表の行>' }
{ field: 'output', spelling: '電圧パルス／オープンコレクタ（ディップスイッチ選択）',
  classes: ['電圧パルス5V', '電圧パルス12V', 'オープンコレクタ'], mode: 'selectable',
  src: '<設計文書の表の行>' }
```

- 分類名そのものも閉じた一覧としてモジュールに1回だけ宣言する（分類名の綴り間違いを検査で落とすため）。

### 3-2. 各行の出典を設計文書に記録する

- 対応表の中身は、別の文書 PR（8章の順 3）で設計文書の表として起こす。**1行ごとに**
  綴り／分類／出典（資料名・版・ページ、または「依頼者の判断（日付）」）／「同じ分類」とした理由 を書く。コードの `src` はその行を指す。
- **出典が「読めない」行は表に入れない。** 入れない綴りは 3-3 の検査で落ちるので、黙って一致にはならない。
- **WGP-FZ の入力コード `14` は、接点入力を「含まない」として書く**（D1。7章）。

### 3-3. 対応表に無い綴りを NG にする検査（`verify-data` に足す）

検査名に件数を入れる（既存の「追加レコードの規約（現在 N 件）」と同じ形）。設計報告 A-3-3。

1. `絶縁変換器の信号名 N 種すべてが分類表に行を持つ（表に無い綴り 0）` … 表に無い綴りは NG。「解析できないから一致とみなす」経路を作らない
2. `分類表の N 行すべてに出典の記載があり、設計文書の表に同じ綴りの行がある`
3. `分類表の行はすべて data の綴りに使われている（使われない行 0）` … データに無い綴りの行は、型式コード表からの先回り（ルール2 と同じ構造）になるため
4. `分類表の分類名はすべて宣言した一覧にある`

### 3-4. 値が集合になるものの比べ方

- `mode` は2種類（設計報告 A-3-4）：
  - `selectable` … 型式1つが複数の値を持つが、現場ではそのうち1つに設定されている（WGP-FZ の第1出力 `F`、WGP-FV の入力 `14`）
  - `single` … 1つの値
  - 同時に複数を受ける `accepts` は、該当する実例が無いので作らない
- 比べた結果（6章の `relation`）と状態：

| 関係 | 意味 | 状態・扱い |
|---|---|---|
| `equal` | 同じ集合 | 同じ |
| `covers` | 候補が基準をすべて含む（例：基準 MS3749 の 12V 固定 → 候補 FZ の `F`） | 候補が `selectable` なら現場で確認（候補のスイッチを基準の設定に合わせる） |
| `coveredBy` / `overlap` | 候補が基準の一部しか含まない（例：基準 FZ の `F` → 候補 MS3749 の 12V 固定） | **`classMatch` に出す**。現場で確認（基準で今使っている設定が候補の値に入っているか）＋2-5 の問い（D4） |
| `disjoint` | 重ならない | `classMatch` に入れない |

- **`coveredBy` / `overlap` を出す根拠**（D4）… 設定は現物を見れば分かる。「今の設定は何か」の問いと
  「現場で確認」の印を必ず付ける。

### 3-5. 向きのある条件の検査

- `covers` は向きがある。実データに向きの違う組が実在する（`fcd064a` で実測：`MS3749-A-D44/H` → `WGP-FZ-14FK-1` は第1出力が `covers`、逆向きは `overlap`）。
- `tools/test-insulation-response.mjs` の形に倣い、**別ファイル**で次を見る（設計報告 A-3-5）：
  1. 向きの違う組が実データに1本以上あること（件数を名前に入れる）
  2. その組はすべて「候補のほうが広い」向きであること
  3. 比べ方を対称なもの（`overlap` 扱い）に差し替えると、向きの違う組が0本になること（空振りしていないことの担保）
- `test-compat.mjs` の「候補の関係が対称」の対象には入れない（名前が実態を語らなくなる。`responseWithin` の JSDoc と同じ理由）。

## 4. 組み合わせ

### 4-1. 候補の形：最初から「部品の並び」で持つ。作れる並びは狭く始める

```js
{ tier: 'rework', parts: [{ id: '<登録済みレコードの id>', qty: 2 }], rule: '<ルール名>', checks: [...] }
```

- 単体の候補も `parts: [{ id, qty: 1 }]`。
- **最初から並びにする理由**（設計報告 A-4-1）… 新しい口は新設なので、後から形を変えると口を使う全カテゴリ・カード・
  件数表示・検査を一度に直すことになる。形を先に広く取り、中身（作ってよい並び）を狭くしておくほうが変更が小さい。
- **作ってよい並びは「同じ型式 × 2台」だけ。**
  - 違う型式の組（例：FZ-14FK-1 ＋ FZ-14FC-1）は**当面出さない**（D3）。在庫の所在を持たないので「1台ずつならある」を
    アプリは知らず、組を全部並べると読めなくなる。実例が出たら再検討する。
  - 同じ型式に限るもう1つの理由は 4-2（接点入力の検出電圧。D2）。
  - 付属品（補助接点ユニット）は登録データが無いので作れない（`docs/design-c-legacy-inverters.md` 6-10 の
    「データが無いまま画面に出せば表示側に直書きすることになる」と同じ）。

### 4-2. 「2台で各々から1点ずつ出力」の読み方（依頼者の決定、2026-09-27）

> **「2台で各々から1点ずつ出力でも可」は「出力ごとに1台」と読む。
> 1つの接点を2台の入力に並べてつなぎ、1台目から第1出力、2台目から第2出力を取る。**

- **根拠** … 依頼者の決定（D2）。要件の原文は `docs/msystem-wrpp-verified.md` 4章。
- **設計報告の推奨（相ごとに1台：A相用1台・B相用1台）とは違う決定です。**
- この決定に伴って決めたこと：
  1. **組み合わせは同じ型式の2台に限る。** 接点入力は機器の側から検出電圧を掛けるので、検出電圧の違う機種を並べると、
     互いに電流が流れ込むおそれがある（依頼者の決定）。
  2. **確認項目に「1つの接点に2台分の検出電流が流れる」ことを出す**（依頼者の決定）。
     参考：接点に流す電流は WRPP 5V DC／10mA、WGP-FZ（入力 14 の ON-OFF パルス）OFF時5V・ON時1mA
     （`docs/msystem-wrpp-verified.md` 4章。どちらもデータには無い）。
  3. **基準機が2相で B相を使っていない場合は、2出力の機種1台で A相の出力2点をまかなえる。**
     「B相の配線を使っているか」の問い（2-5）と組み合わせて扱う（依頼者の決定）。
     - この候補は入力の相数が基準と違うので `classMatch` の条件（相数が同じ。5-1）に当たらず、
       B相を使わないという配線の条件付きなので `rework` の段に出す（`parts` は `qty: 1`）。
       確認項目の「入力の相数」は「違う」になり、問いを参照する（この文書の設計）。
  4. **B相を使っている場合の置き換え（相ごとに1台）を候補に出すかは、決めていない**（9章の未決）。
- WRPP の構成は「2相（A相・B相）× 2出力」で、相ごとに第1出力・第2出力を持つ（`docs/msystem-wrpp-verified.md` 3章）。

### 4-3. 登録データにするか、計算で作るか

- **同じ型式の台数増は計算で作る。種類の違う機器の組（接触器＋サーマル、補助接点ユニットの追加）は、
  必要になったときに登録データとして出典つきで持つ**（設計報告 A-4-2）。
- **引き継ぎ書 §2 ルール2（型番を推測・生成しない）との関係：**
  - 計算で作っても新しい型式の文字列は1つも生まれない。部品はすべて登録済みの id で、画面の型式は登録された綴りのまま（1-2 の3）。
  - ただし「2台で代わる」は機能についての主張になる。だから：
    - 組み合わせのルールは**カテゴリが名前付きで宣言**し、ルールごとに出典を設計文書に書く
      （4-2 のルールの出典は、依頼者の要件 2026-09-26〔`docs/msystem-wrpp-verified.md` 4章〕と依頼者の決定 2026-09-27）
    - 結果は `rework` の段にだけ出し、確認項目と「現場への問い」を必ず付ける
  - 種類の違う機器の組は、組ごとに成り立つ根拠（取付・配線）が違うので、登録データが向く。
- サーマルの `mountsOn`（取付可能な接触器）は既に登録データで、接触器＋サーマルの組の材料になるが、この設計の範囲外
  （最初の2カテゴリに要らない）。

### 5-4. 3つに同じ形が当てはまるか

**当てはまる点** … 段の持ち方（振り分け＋加算）／確認項目の4状態／共通の比べ方（集合の `covers` は区間の包含・補助接点の数の大小にも使える）／
現場への問いを1回だけ出す形。

**当てはまらない点**（設計報告 A-6-4）

1. **「別メーカー品は完全一致と別のゾーン」**（11-2-1 ①）は、接触器・サーマルでは既に成り立っていない。
   今の③の 1176/1398（接触器）・732/910（サーマル）が別メーカーで、`gate` は窓・重なり率で、完全一致ではない。
   絶縁変換器は 0/81 で、信号名の綴りが完全一致を支えている。
   → **接触器・サーマルの今の③は、そのカテゴリが新しい仕組みを使い始めるまで今の見出し「当アプリの判定による候補」のまま**（D13）。
   使い始めるときに見出しの下へ条件の1文を添える。
2. **「判定条件がすべて一致」という見出し**は、窓で拾うカテゴリでは「値が一致」と読まれるおそれがある
   （S-N35 34A の候補に 26A が9件）。→ 同じく D13。
3. **「配線変更または台数増が必要」の名前に入らないもの** … サーマルの「接触器も交換が必要」、接触器の「補助接点ユニットの追加」。
   → D12（今の段のまま確認項目で示す）。
4. **分類（`classMatch`）が要るのは絶縁変換器だけ。** サーマル・接触器は数値の窓・区間で比べる。
5. **比べる量の型が違う** … 絶縁変換器＝名前と集合、サーマル＝区間、接触器＝数値の窓と接点の数。共通の比べ方（6章）で吸収する。
6. **データの側が支えられない項目** … サーマルの整定範囲の意味、接触器のコイル（10章の課題）。形の問題ではなく出典の問題。

## 6. 一致の結果の共通の形

### 8-3. PR の分け方と順序

Open の PR は1件ずつ。設計文書の PR にコード変更を混ぜない（`CLAUDE.md`）。設計報告 A-8。

| 順 | 種類 | 中身 | 前提 |
|---|---|---|---|

| 3 | 文書 | 絶縁変換器の分類表と、各行の出典 | D1（入力 14 は「含まない」で書く） |

  その分、2 の口は最小にし（段・4状態・比べ方・問いだけ）、8 で見直す前提にする。

## 10. 課題（設計とは別に記録するもの。決めていない）

データの出典の問題で、この文書の設計では扱いを決めていません。値は `fcd064a` の `data/*.json` から数えました。

1. **電磁接触器・電磁開閉器の操作コイル電圧が 124件すべて `AC200V` で、出典が無い。**
